`watch` now deletes by default, and handles moves, renames and whole folders.

- **Behaviour change:** `looker-sync watch` now applies local deletes to your Looker dev
  workspace. Delete a synced file locally and it is deleted in Looker, with a `deleted` line. Pass
  `watch --no-delete` to get the old behaviour back exactly: local deletes are only reported.
- A rename or move writes the new path, verifies it by read-back, and only then deletes the old
  one. This works for many files at once and for whole folders, nested ones included. Copies are
  written like any new file.
- Deleting or moving a folder locally also removes the folder in Looker. Nested folders are created
  in Looker as needed.
- Batches now run in parallel, up to 8 at a time.
- Guards: nothing git does causes a delete, including `git init` after `watch` started. An atomic
  save never deletes: a vanished file waits 1.5 s and is checked again. Only files this run saw
  vanish are deleted, and files that exist only in Looker are left alone. A file changed in Looker
  is held unless you pass `--force`, and every hold also holds deletes. The 200 file ceiling
  counts deletes too.
- `DELETE /projects/{p}/directories?path=...` answers 200 and is recursive. It removes a folder's
  files with no warning. `watch` re-lists the folder from Looker right before the call and leaves
  the folder alone if the listing is not what it expects.
- Still no runtime dependencies.

Measured on Linux against a sandbox project, on this code. One run unless a count is given:

| delete a file, local delete to `deleted` line, n=3 | 3.069, 3.130, 2.997 s |
| rename a file, to `deleted` line | 2.953 s |
| create 6 files in nested new folders | 3.193 s, 44 API calls |
| `mv` 5 files into another folder | 8.980 s, 51 API calls |
| rename a folder of 10 nested files, n=2 | 8.800, 14.986 s, 102 and 105 API calls |
| `rm -rf` a folder of 10 nested files, n=2 | 10.150, 9.046 s, 37 API calls each |

Limits, stated plainly:

- The final live run was stopped early. Regression and bulk timings finished and passed. Live
  checks of the folder guard, of whether Looker's file listing shows every file type, of failure
  handling under load, and of an Explore change through a new view, include or model were not
  run. Tests against a fake Looker cover the guards and failure handling.
- A folder delete is recursive. A file type that Looker's file listing does not show would be
  removed with its folder, and a file created in Looker in the one round trip between the check and
  the delete would be lost. Use `--no-delete` if that matters to you.
- A mistaken local `rm` deletes the file in Looker too, and uncommitted work in the workspace goes
  with it. `git clean` is seen as a local delete and is applied.
- Not run on a Mac in this release.
- What an open browser IDE tab does on stale content was not tested. A real branch switch in the
  Looker IDE was not tested live either.

Upgrade with `uvx looker-sync@latest`.
